# Workflow coverage

Build a coverage matrix from the current source and selected task before
reviewing screens. This inventory is a starting map, not a completed audit or
evidence that its tests passed. Apply the lenses requested by the user; a whole-app
UI/UX review uses usability, accessibility and wording. Recheck the map when
workflows change.

Use [TASKS](../../../../docs/TASKS.md) for the current checkpoint,
[SPECIFICATION](../../../../docs/SPECIFICATION.md) sections 2–4, 10–13 and 18 for
requirements, and [ACCEPTANCE](../../../../docs/ACCEPTANCE.md) for evidence and
remaining release checks. Read current password, size, retention and model
policies there instead of freezing those values in the review report.

Use the coverage fields and statuses in [SKILL.md](../SKILL.md), starting each row
as **not reviewed**. Distinguish source inspection, browser observation, automated
checks and manual device or assistive-technology testing. Link existing tests;
record actual commands and outcomes only when run. The tables describe implemented
UI unless stated otherwise. Test links identify coverage to inspect, not fresh
results.

## Optional and unverified coverage

- **Browser model research:** separate experimental component, outside learner
  navigation. Review only when requested: availability, explicit download
  consent, progress/failure, cancel/unload/delete cache, synthetic evaluation
  and result export. Inspect [Research](../../../../apps/web/src/Research.tsx)
  and [Research tests](../../../../apps/web/tests/Research.test.tsx); do not
  download a model during a routine review.
- **Specification versus UI:** section 3 describes administration/evaluation
  and redacted usage more broadly than the four Settings sections. Do not infer
  an implemented dashboard, learner-disable action, research entry point or
  evaluation runner from a specification label. Confirm source/task status
  before adding such a journey to the implemented inventory.
- **Existing follow-ups:** [ACCEPTANCE](../../../../docs/ACCEPTANCE.md) records
  limited History pagination and the backend administrator-authorship question
  despite learner-only practice UI. Carry their existing evidence forward; do
  not label them newly observed browser findings.
- **Separate acceptance evidence:** physical iPhone Safari/Android Chrome,
  camera/HEIC, installed PWA/background behavior, manual accessibility, actual
  tutoring quality and host recovery remain distinct checks. Chromium
  emulation, screenshots, mocked responses and source inspection do not prove
  these outcomes.

## Checks across every selected journey

Apply the following checks as relevant to the requested lens and available evidence
method; a focused copy review does not require rendered or accessibility testing.
For a full UI/UX review, check desktop and narrow/portrait layouts, touch targets, zoom/reflow, keyboard
order/visible focus, headings/landmarks, labels/descriptions, announced
errors/status, loading/empty/error/success states, contrast, non-color-only
meaning, accessible mathematics and reduced motion. Use the accessibility
reference for WCAG 2.2 AA review details.

Trace role/ownership, processing-location disclosure, content clearing,
pending-operation guards, cancellation and recovery. Copy should identify what
happened, what is saved and the available next action. Hidden buttons and a
successful visual tour do not establish backend authorization/privacy.
